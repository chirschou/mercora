## 1.需求

### 目标

用户原话：页脚 Explore（About Us、Privacy Policy、Terms of Service、Blog）与 Support（Contact support、Privacy、Terms）「这些里面的详细信息 按实际可以运营的标准帮忙做好 有关公司地址相关信息你完成后 我自己去修改」；追加：「至少写 5 篇原创 最好是能修改一下跨时间段的」。

Melt Party（https://melt.party）是英文店面，卖科技感户外运动装备。本需求要做到：

1. 页脚 7 个链接在本地和线上都能打开，不出现 404，内容达到真实店铺上线运营的水准，不再是样例文案。
2. 隐私政策和服务条款按本站**实际**的数据处理和交易规则来写，每条事实都能在代码或文档里找到出处。代码里找不到依据的，用保守表述，不编造数字或承诺。
3. 公司主体相关信息（法定名称、注册地址、注册号、适用法域）一律写成统一格式的占位符，由用户上线后自己替换。不得编造公司信息。
4. Blog 至少 5 篇原创文章，发布日期分散在近几个月，均不晚于 2026-11-09。每篇都能在后台 Blog CMS 正常编辑和保存。
5. 每个页面都标注「Last Updated」。

### 内容规格

通用要求（所有页面和文章都适用）：

- 语言：美式英语，面向消费者，平实可读。不出现中文，不出现「AI-powered eCommerce platform」这类平台自述。
- 只写可核实的事实，依据见「2.分析过程 / 数据处理事实清单」。代码里没有依据的数字或承诺一律不写，或改为保守表述。
- 品牌名用 `Melt Party`，助手名用 `Floe`，支持邮箱用 `support@melt.party`（已核实：`wrangler.jsonc:141`）。不引入任何未核实存在的邮箱或电话，例如不写 `privacy@melt.party`。
- 正文不写 `<h1>`，页面标题由 Hero 渲染。只用清洗白名单内的标签（`lib/utils/sanitize-html-policy.ts:1-16`：p、h2、h3、ul、ol、li、strong、em、a、table、thead、tbody、tr、th、td、hr、blockquote 等）。
  - 白名单**不含** `id` 属性，不能写页内锚点目录。章节导航由法律页模板按 `<h2>` 自动生成（`PageRail`）。
  - 链接只用相对路径（如 `/account/orders`）或 `mailto:`、`https:`。
- 每页的「Last updated」字样必须**逐字**如下，日期统一为 `November 9, 2026`：
  - 法律页（template `legal`）：正文第一个元素写 `<p><strong>Last Updated:</strong> November 9, 2026</p>`。
    - 页面会把这行提取成顶部标签。正则要求大写的 `Last Updated:` 并且必须在开头（`lib/cms/page-sections.ts:29`）。
    - 紧接着的第一段 `<p>` 会被提为 Hero 导语，所以第二个元素写一段 1–2 句的导语。
  - About、Contact（template `about` 回退为 `story`，以及 `contact`）：先设置 `excerpt` 作为 Hero 导语。
    - `excerpt` 非空时不会把正文第一段提为导语（`app/[slug]/PageRenderer.tsx:45-51`）。
    - 正文第一个元素同样写 `<p><strong>Last Updated:</strong> November 9, 2026</p>`，它会作为正文首行显示。
    - 不能不设 `excerpt`，否则 Hero 导语会变成「Last Updated: …」。
- 每页 `content` 少于 100,000 个字符，这是后台保存校验的上限（`lib/models/pages.ts:492`）。

### 决策缘由与已踩坑

1. **Last Updated 的格式有硬约束**：正则是 `^\s*<p><strong>Last Updated:</strong>…</p>`，大小写敏感于字面量 `Last Updated:`，并且必须在 lead 开头。写成「Last updated」或放进 h1 后面都不会被提取。story/contact 模板不提取它，必须设置 excerpt，否则 Hero 导语会变成这一行。
2. **h1 重复**：0026 只替换了品牌词，About 的 `<h1>About Melt Party</h1>` 与标题「About Us」不一致，因此不会被剥离，线上至今显示两个标题。新内容一律不写 h1。
3. **后台 Blog 保存的隐性校验**：每次保存都会提交 coverImageUrl、html、tags 和分钟精度的 publishedAt。只要迁移数据里的封面不是允许来源，或 html 不是清洗稳定形态，或时间戳带秒，后台「原样保存」就会报错或悄悄改动数据。因此验收第 13 条要求等价断言。
   - 实现建议：先把起草好的 HTML 用 `sanitizeRichHtmlServer` / `sanitizePageHtmlServer` 处理一遍，把输出写进迁移。
   - 封面不要写死 `https://images.melt.party/...`：本地或其他 CDN 配置下会被拒绝。用 `/products/...` 相对路径。
4. **测试库假设**：`blog-schema.test.ts` 把 0019 的「空库」性质写成了全量迁移后的断言。0027 写入内容后它必然失败。正确改法是切片到 0019，不能删断言。
5. **知识库是第二事实源**：Floe 用 `data/r2/knowledge_md` 回答问题，里面有 example.com、虚构电话、Oregon 仓库等样例信息。条款中的数值尽量与知识库一致（退货、保修、服务时间），不一致的样例信息（门户、电话、仓库）不采用，并另立 BACKLOG。
6. **站点中立性**：`AGENTS.md` 和 `docs/content-publishing.md` 把仓库定位为可复用的店面。0027 写入的是 Melt Party 自有内容，会进入任何应用迁移的库。这与 0003/0026 的先例一致，且仓库已整体改名为 Melt Party（FEAT-20261108-02），所以接受，并按范围 B.4 在文档中写明。

   - (1) 快照：
     ```sql
     INSERT INTO page_versions (page_id, title, content, excerpt, meta_title, meta_description, meta_keywords, version, change_summary, created_by)
     SELECT p.id, p.title, p.content, p.excerpt, p.meta_title, p.meta_description, p.meta_keywords, p.version, 'Snapshot before FEAT-20261109-01 content rewrite', 'system'
     FROM pages p
     WHERE p.slug IN ('about','privacy-policy','terms-of-service','contact')
       AND NOT EXISTS (SELECT 1 FROM page_versions v WHERE v.page_id = p.id AND v.version = p.version);
     ```
   - (2) 页面 UPSERT：`INSERT INTO pages (...) VALUES (...) ON CONFLICT(slug) DO UPDATE SET title=excluded.title, content=excluded.content, excerpt=excluded.excerpt, meta_title=excluded.meta_title, meta_description=excluded.meta_description, template=excluded.template, status='published', show_in_nav=excluded.show_in_nav, sort_order=excluded.sort_order, is_protected=0, updated_at=unixepoch(), version=pages.version+1 WHERE pages.content IS NOT excluded.content OR pages.title IS NOT excluded.title OR pages.excerpt IS NOT excluded.excerpt OR pages.meta_description IS NOT excluded.meta_description`。WHERE 条件保证重跑是空操作。
   - (3) 新版本记录：与 (1) 结构相同，change_summary 写 `FEAT-20261109-01 content`，同样带 NOT EXISTS。新建的 contact 页因此得到 version 1 记录，与 `createPage` 的行为一致。
   - (4) 分类：`INSERT INTO blog_categories (name, slug, description) VALUES … ON CONFLICT(slug) DO NOTHING`。
   - (5) 文章：`INSERT INTO blog_posts (…, category_id, …) VALUES (…, (SELECT id FROM blog_categories WHERE slug='gear-guides'), …) ON CONFLICT(slug) DO NOTHING`。
   - SQL 字符串里的单引号写成 `''`。不用 `date('now')`，否则日期会随应用时间变化，这正是 0003 的坑。迁移文件头部注释写明：用途、expand-only、覆盖页面且有快照、不可下迁移、回滚方式（在后台从 page_versions 取回）。

### 风险与控制

- **R1 法律文本风险**：文本按通行实践起草，不是法律意见，不同法域的强制要求（如 EU 消费者撤回权、加州自动续费法）可能需要补充。控制：
  - 订阅条款写明续费、取消方式和不按比例退款。
  - 不写高风险的仲裁条款。
  - 上线前是否请律师审阅，由用户决定，在交付汇报中提醒。
- **R2 订阅同意版本**：线上已有的订阅同意记录（若有）引用的 2026-09-07 版本从未公布。本需求只保证今后一致，历史记录不追溯，在汇报中提醒用户。改版本号后，正在重试中的旧版本发起可能因 consent 不一致而需要重新提交，影响面很小。
- **R3 Floe 与条款口径不一致**：知识库里的 example.com、电话、Return Portal 仍会被 Floe 引用。控制：作为 BACKLOG 待办，后续另开 FIX 修改 knowledge_md 并重建向量；涉及生产 R2/Vectorize，需单独确认。
- **R4 生产后台改动**：线上 HTML 在 2026-11-09 核实为种子原文。从核实到部署之间如有后台改动，旧内容在 page_versions 快照中，可人工找回。
- **R5 Cookie 表准确性**：Clerk、Stripe、Cloudflare 的 cookie 名来自领域常识，没有在本会话实测。控制：验收第 20 条要求线上实测后定稿。
- **R6 邮件页脚地址**：在 `STORE_POSTAL_ADDRESS` 配置之前，所有邮件都显示占位句。这不在本需求范围内，作为关联配置提醒用户。
- **R7 部署**：远端迁移由 Workers Builds 的 `deploy:ci` 在合并后应用（`docs/DEPLOYMENT_SETUP.md:312`）。合并、部署、线上验收都需要用户或编排方另行确认。

### 实现中的决策与偏差（编排方授权代决）

1. **页面 UPSERT 的覆盖字段比「实现方案」多 3 个**：除方案列出的字段外，还覆盖 `meta_keywords`、`published_at`、`nav_title`（都写 NULL），WHERE 条件同时比较这些字段。理由：这三个字段会影响页脚文案（`nav_title`）、页面是否可见（`published_at`）和 SEO。只有统一覆盖，「全新库与生产库结果一致」才对任何后台改动都成立。`updated_by`、`custom_css`、`custom_js`、`parent_id`、`required_roles` 不碰。
2. **Footer 查询**：`getPageBySlug("contact")` 并入原有的 `Promise.allSettled`。查询失败或页面不存在时回退 mailto。contact 页 show_in_nav=0，所以不能复用 `getNavigationPages` 的结果。
3. **blog-schema 测试整文件停在 0019**：`beforeEach` 改为只应用到 0019，没有删除任何断言。原因有两个：
   - 当前 `@cloudflare/vitest-pool-workers` 0.22 实测按**文件**隔离存储，同一文件内的用例共享一个库，README 写的「按用例隔离」与实测不符。
   - 约束用例写死了 `category_id 1` 和 `DELETE ... WHERE id = 1`，隐含「分类表为空」的前提。
   
   模板用例停在 0019 时点，结果不变（模板只在 0003、0019 写入）。
4. **`d1-harness.test.ts` 补 0027**：它写死了完整迁移清单，本文档「受影响的测试」漏列了它。按原意在清单末尾补上 0027，与之前加 0026 时的做法一致。
5. **0027 测试拆成两个文件，清洗断言放在单测**：
   - 同一文件内共享存储，「全新库」和「已有生产库」需要两种起点，所以分成两个文件。
   - Workers 测试池加载不了 sanitize-html（postcss/nanoid 的 CJS 互操作报错），现有的 `content-publication-models.test.ts` 也因此把它 mock 掉。所以「`sanitize*Server(x) === x`」放在 node 单测里，直接解析 0027 的 SQL 字面量来断言；集成测试按惯例把清洗器 mock 成恒等函数。两者合起来等价于验收第 13、14 条的要求。
