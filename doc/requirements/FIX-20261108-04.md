## 1.需求

### 现象

生产 `https://melt.party/sign-in` 返回 404。未登录访问 `/admin/*`（`middleware.ts`）、`/account/*`（`app/account/**`）以及受保护 CMS 页（`app/[slug]/page.tsx`）都会重定向到 `/sign-in?redirect_url=…`，但 `app/` 下没有 `sign-in`、`sign-up` 路由，用户无法登录。

### 复现步骤

1. 以基线 `release@166fb48` 构建并访问 `/account`（未登录）。
2. 被重定向到 `/sign-in?redirect_url=/account`。
3. App Router 中没有与 `/sign-in` 匹配的路由（`/sign-in` 落到 `app/[slug]`，`sign-in` 是保留 slug，无 CMS 页），返回 404。

### 期望与实际

| 项 | 期望 | 实际 |
|---|---|---|
| `GET /sign-in`、`/sign-in/*` | 渲染 Clerk `<SignIn />`（path routing），登录后按 `redirect_url` 回跳 | 404 |
| `GET /sign-up`、`/sign-up/*` | 渲染 Clerk `<SignUp />`，可处理 Clerk 邀请 ticket（`__clerk_ticket`） | 404 |
| 维护模式下未登录管理员访问 `/admin` | 能到达 `/sign-in` 完成登录（middleware 承诺维护期 admin 可用） | 重定向到的 `/sign-in` 被维护页拦截为 503 |
| Clerk 组件内跳转（SignIn ↔ SignUp、`SignInButton` 等） | 指向本站 `/sign-in`、`/sign-up` | 未配置 `signInUrl`/`signUpUrl`，落到 Clerk Account Portal |

### 范围与非目标

- 新增 `app/sign-in/[[...sign-in]]/page.tsx`、`app/sign-up/[[...sign-up]]/page.tsx`；`ClerkProvider` 显式传 `signInUrl="/sign-in"`、`signUpUrl="/sign-up"`；middleware 让这两个路由跳过维护页。
- 非目标：不改 Clerk 实例设置、不改 `wrangler.jsonc`、不新增环境变量或写任何 key；不改现有重定向调用点；不迁移 `middleware.ts` → `proxy.ts`。

### 验收标准

1. `/sign-in`、`/sign-up` 均有 App Router 可选 catch-all 路由，分别渲染 Clerk `<SignIn />`、`<SignUp />`，且不传 `forceRedirectUrl`/`routing` 等会覆盖 `redirect_url` 或 path routing 的属性。
2. middleware 对未登录的 `/sign-in?redirect_url=/admin`、`/sign-in/factor-one`、`/sign-up?__clerk_ticket=…` 不重定向（无循环）；维护模式开启时这两个路由不返回 503，而店面首页仍返回 503。
3. `ClerkProvider` 的 `signInUrl`、`signUpUrl` 指向 `/sign-in`、`/sign-up`。
4. 复现转回归：新增 `tests/unit/app/auth-routes.test.ts`，在基线（无路由、无维护豁免、无 Provider URL）报红，修复后全部通过。
5. `typecheck`、`lint`、`scan:tokens`、`npm test`（全量）、`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_placeholder npm run build:worker` 通过。

## 2.分析过程

- 来源：编排方派单（328c8311，2026-11-08）。
- `@clerk/nextjs@7.8.3` 的 `SignIn`/`SignUp` 通过 `useEnforceCorrectRoutingProps` 从当前 pathname 去掉 catch-all 段推导 `path`，默认 path routing；因此页面只需放在 `[[...sign-in]]` 可选 catch-all 下、不传属性。可选 catch-all 同时匹配 `/sign-in` 本身与 Clerk 的子步骤（`/sign-in/factor-one`、`/sign-in/sso-callback`、`/sign-up/continue` 等）。
- `redirect_url` 查询参数由 Clerk 组件原生读取，优先级低于 `forceRedirectUrl`、高于 fallback；所以页面不得传 `forceRedirectUrl`，否则会覆盖调用点给的回跳地址。
- 邀请 ticket：Clerk 邀请链接带 `__clerk_ticket`、`__clerk_status`，`<SignUp />`（新用户）与 `<SignIn />`（已有用户）原生处理，页面无需额外代码；middleware 不改写查询串即可保留。
- `signInUrl`/`signUpUrl`：未配置时 Clerk 组件之间的跳转与 `SignInButton` 非 modal 场景会去 Account Portal。可用 `NEXT_PUBLIC_CLERK_SIGN_IN_URL` 环境变量或 Provider 属性；环境变量需改构建变量（禁区外资源），选 Provider 属性，静态、可测。
- 循环重定向：middleware 只对 `/admin` 前缀做未登录重定向，`/sign-in`、`/sign-up` 不在其中，不会循环；已登录用户访问 `/sign-in` 由 Clerk 组件自行跳到回跳地址。
- 维护模式坑：基线 middleware 维护页拦截除 `/admin`、`/api/admin`、`/api/mcp` 外的一切路径，而 `/admin` 的未登录重定向目标 `/sign-in` 会被拦成 503，维护期管理员无法登录，违背「维护期 admin 仍可用」的约定。故 `/sign-in`、`/sign-up`（含子路径）一并跳过维护检查。
- 路由优先级：静态段 `sign-in` 优先于 `app/[slug]` 动态段；`sign-in`、`sign-up` 已是 CMS 保留 slug（`lib/models/pages.ts`），不冲突。
- 店面 token：页面容器只用 `bg-surface`、`text-foreground` 等 token 类；Clerk 组件外观沿用 `ClerkProvider` 已有的 token 化 `appearance`。
